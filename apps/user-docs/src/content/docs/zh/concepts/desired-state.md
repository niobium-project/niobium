Niobium 产品从构建时代码开始。作者构造带类型的模型；固定能力库随后根据此模型、安装输入和观察结果提出期望资源。

[DSL 教程](/zh/tutorial/)用 Starlark 产品走通此流程。当前 Component-v2 运行配置使用命令行操作和用户范围根目录。执行资格单独记录在[状态与平台](/zh/status/)上。

## 编译后的模型

原生 Zig、作者 C API 和 Starlark 构造同一个产品模型。作者代码中的变量、函数、条件和循环在构建时执行。输出的 JSON 是由共享编译器流水线消费的编译器产物。

模型固定产品身份和发布序号、带类型的输入、内容身份、逻辑根目录、授权、观察和能力调用。每次调用选择精确的库实现及其导出的 WIT 函数。WIT 是定义参数和结果类型的 WebAssembly Component 接口语言。

编译器检查这些类型及所选运行时配置，然后打包完整的预编译运行时。交付的安装器包含模型和固定库；安装时不执行作者源码。

## 安装时的期望资源

运行时解析带类型的输入值和声明的只读观察，再求值编译后的调用图。生成计划的调用返回期望容器，其中包含获授权的根目录、授权、相对前缀，以及显式文件和目录访问策略。

宿主检查内容身份、路径、所有权、访问权限上限、冲突和预算。在执行[事务](/zh/concepts/transactions/)之前，它冻结获接受的内容和原生资源清单。库失败会中止求值，不能被当作成功的空计划。

例如，教程将 `enabled` 绑定到文件库请求。以 `enabled=false` 重配置会产生空的期望内容集，移除先前发布的文件，同时保留安装状态。

## 产品策略与路径

作者和库负责选择与布局策略。产品声明逻辑根目录 ID，调用时将它们绑定到绝对目录。宿主验证映射，拒绝不兼容的所有权或不安全的根目录关系。

教程声明 `application`，并以 `--root application=<absolute-directory>` 绑定它。教程请求此根目录内的 `hello` 前缀。此运行配置不要求由框架选择的产品目录或固定的组件选择 schema。

产品模型版本和每次调用的状态版本有独立的兼容性规则。改变它们需要显式且适用的升级或迁移声明。见[编译后产品契约](https://github.com/niobium-project/niobium/blob/main/docs/spec/program-image.md)和[迁移契约](https://github.com/niobium-project/niobium/blob/main/docs/spec/migration.md)。
